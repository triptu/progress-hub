# Set up progress on this machine

You are setting up the progress hub for the person who gave you this file. Do each step yourself. Ask them only where a step says to.

1. **Git and Bun.** Install whichever is missing. Bun is at https://bun.sh. A fresh Bun is in `~/.bun/bin`, which this shell has not read yet, so add it to `PATH` before the next steps.
2. **Get the code.** If this repo is not on the machine yet, clone https://github.com/triptu/progress-hub into a folder that lasts, such as `~/code/progress-hub`, not a temporary one. Setup builds from the clone, and an update is a pull and setup again.
3. **Run `bash setup.sh`** in the clone. It builds `progress` and puts it in `~/.local/bin`. It prints an `ok` line for what is ready and a `todo` line for each thing left to do.
   - Do every `todo` you can. The usual one is putting `~/.local/bin` on the `PATH` the person's agents start with, in their shell profile.
   - Tell the person about a `todo` only they can do, such as signing in to `gh`. It is optional: `gh` adds pull request titles.
   - Pages are kept in `~/progress`. If the person wants another folder, run `PROGRESS_HOME=/that/folder bash setup.sh` instead.
   - On macOS setup starts the hub as a login service. On Linux nothing starts it. Run `progress serve` the way that machine keeps a program running (a systemd user unit, for one), or tell the person to start it. Check that the address it prints answers.
4. **Tell their agents.** Add the two lines below to the instruction file each of their agents reads on every task, such as `~/.claude/CLAUDE.md` or `~/.codex/AGENTS.md`. Ask which agents they use if you can't tell.

   ```
   For any task I will come back to, run `progress new "<title>"` when you start, and keep the page it
   prints current as you work. Run `progress format` once to read the page format.
   ```
5. **Make the first page.** Run `progress new "Set up progress"` for this session. It prints the page's path and its link in the hub. Run `progress format`, fill the page in as it says, and run `progress check <that path>` to see what the hub reads from it. The hub shows a changed page within a few seconds.
6. **Report.** Give the person the link `progress new` printed, the folder their pages are in, the instruction files you changed, and any `todo` left for them.

## Later

- **Update.** Pull in the clone, then run `bash setup.sh` again. On Linux, restart `progress serve` after it.
- **Move the pages.** Move the folder, then run `PROGRESS_HOME=/new/folder bash setup.sh`.
- **Remove.** On macOS, run `launchctl bootout gui/$(id -u)/progress.hub` and delete `~/Library/LaunchAgents/progress.hub.plist` and `~/Library/Logs/progress.log`. On Linux, stop `progress serve` and undo whatever you set up to keep it running. Delete `~/.local/bin/progress` and `~/.config/progress`, and take the two lines out of the instruction files and the `PATH` line out of the shell profile if you added one. An older setup may have made a Tailscale forward for the hub's port: `tailscale serve status` shows it, and `tailscale serve --http=4747 off` turns it off. Leave the pages folder unless the person says to delete their pages.

## A central hub

One address that shows every machine's work, answers while the machines sleep, and opens only for the people the person allows. It runs on their own Cloudflare account, behind Google sign-in. Marks can be changed there: a mark made on it reaches the machine at its next send, within a minute when it is awake, and shows on the central hub until then. Todos are changed only on a machine's own hub. A machine running an older build of progress ignores marks made on the central hub: they keep showing there and never reach it, until it is updated. Do this only when the person asks for it.

1. **What they give you.** Ask for the addresses that may sign in: Gmail addresses, or addresses of a Google Workspace domain. Google is the authority for those, and the deploy refuses any other. Ask for the client id of a Google OAuth web client (Google Cloud console, Google Auth Platform, Clients), and the id of the Cloudflare account to use (on the account's home page in the dashboard). Ask whether they want their own domain for it; without one it is at a `workers.dev` address.
2. **Log in to Cloudflare.** In `cloud/`, run `bun install`, then `bunx alchemy profile edit` and connect Cloudflare. The person picks the account in their browser.
3. **Deploy.** In `cloud/`, run `bun run deploy -- --account <account id> --allow them@gmail.com --google-client-id <id>` (add `--domain <host>` for their own domain). When that domain's DNS is not on Cloudflare, it must first be a custom hostname (Cloudflare for SaaS) of a zone that is on the account, pointed there with a CNAME: then also add `--zone <that zone>`, and the hub answers the domain through a route on the zone. It stops unless Alchemy is logged into that account. The first time, it names the account and asks for a yes: show the person the name and let them answer. It prints the hub's address. Its keys are kept in `~/.config/progress/deploys/<account id>/progress-central-prod/`, readable by this user only. Keep that folder; a redeploy from this machine reuses it. What Alchemy deployed is recorded in the Cloudflare account itself, so another machine or a workflow deploys the same hub.
4. **Let Google sign in there.** The person adds the hub's address under "Authorized JavaScript origins" of that Google client. Until they do, Google refuses the sign-in.
5. **Link each machine.** Each machine has its own credential, made on the machine that deployed: in `cloud/`, `bun run credential -- --account <account id> --name <the machine's name>`. It writes the credential to a file and says where. On that machine, run `progress link <address> < <that file>`. It writes `~/.config/progress/central` and restarts the hub, which then sends. A credential lets a machine write only its own works.
6. **Check.** The address shows a sign-in page. After the person signs in, it shows each linked machine's work within a minute.
7. **Remove a machine.** Do this for a machine the person no longer uses, or whose credential was lost. On the machine that deployed, in `cloud/`, `bun run machines -- --account <account id>` lists the machines the hub holds, by id. `bun run forget -- --account <account id> --machine <id>` removes one: the hub forgets its works and files, and refuses its credential from then on. Show the person the list and let them name the id; it must match exactly. A removed machine can come back only with a new credential. Running it again for the same id is safe, and deletes any file of that machine's that was still arriving when it was removed.
8. **Deploy from the repository, if they want a merge to deploy.** `.github/workflows/progress.yml`, at the root of the repository, runs the checks on each pull request and deploys on `main`. It needs the repository's secrets `CLOUDFLARE_API_TOKEN` (a token for that account that may edit Workers, R2, the zone's Worker routes and the account's Secrets Store), `PROGRESS_SESSION_KEY` and `PROGRESS_MACHINE_KEY` (the two values in the deployment folder's `keys.json`, never new ones) and `PROGRESS_ALLOW`, and its variables `CLOUDFLARE_ACCOUNT_ID`, `PROGRESS_GOOGLE_CLIENT_ID` and, for a domain, `PROGRESS_DOMAIN` and `PROGRESS_ZONE`. Set them with `gh secret set` and `gh variable set`, reading the keys from the file and never showing them. Without the variables the deploy is skipped. The deploy stops before it uploads anything if the hub that is live does not take those keys. The machine that deployed keeps its folder: making a credential and removing a machine are still done there.

A machine that stops sending shows its last state, with a note that it has not been heard from, until it is removed. An HTML page that loads files from beside it shows without them, and it can load nothing from another site. Its script can still go to another site and take the page's own text there; the person's own agents wrote it on their own machines, where it can already do that, so the central hub adds nothing to it. A machine's files are deleted from the bucket only when it is removed.
